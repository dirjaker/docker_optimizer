# Docker Image Optimizer — 技术设计文档

> 项目定位：一款基于规则引擎的 Dockerfile 静态分析工具，自动检测 10+ 种优化问题并生成精简后的 Dockerfile。

---

## 第一章 项目背景与价值

### 为什么做

在实际生产环境中，Docker 镜像体积直接影响 CI/CD 构建速度、部署效率和安全攻击面。许多团队的 Dockerfile 存在以下典型问题：

1. **使用臃肿基础镜像**：如 `python:3.11`（920MB）而非 `python:3.11-slim`（130MB）
2. **未使用多阶段构建**：编译工具（gcc、make）残留在最终镜像中
3. **层缓存失效**：多个连续 RUN 指令未合并，未清理 apt/pip 缓存
4. **安全隐患**：以 root 用户运行、使用 latest 标签导致构建不可重复

手动审查 Dockerfile 效率低且容易遗漏，因此开发了一个自动化分析工具。

### 核心价值

- **零外部依赖分析**：纯静态解析 Dockerfile，无需连接 Docker daemon 或镜像 registry
- **精确到行号的定位**：每个 Issue 携带 line_number，即使使用 `\` 续行也能准确定位
- **自动重写 Dockerfile**：不仅指出问题，还自动生成优化后的 Dockerfile
- **多入口使用**：支持 CLI、REST API、Web Dashboard、macOS GUI 四种使用方式

### 面试话术

> "我做了一个 Dockerfile 静态分析工具，能自动解析 Dockerfile 的指令层，通过规则引擎检测 10+ 种常见问题（大基础镜像、未多阶段构建、缓存未清理等），并生成优化建议和重写后的 Dockerfile。工具支持 CLI 和 API 两种使用方式，优化后镜像体积通常能减少 60-80%。技术上用 Python 做指令解析、FastAPI 做 API 服务、Rich 做终端美化输出，数据模型用 Pydantic 做校验。"

## 第三章 核心模块设计

### 3.1 数据模型层 — `models.py`

使用 `dataclass` + `Enum` 定义全链路数据结构，类型安全且可序列化。

**核心数据结构：**

```python
class Severity(str, Enum):
    INFO = "info"
    WARNING = "warning"
    CRITICAL = "critical"

class IssueType(str, Enum):
    LARGE_BASE_IMAGE = "large_base_image"
    CACHE_NOT_CLEANED = "cache_not_cleaned"
    NO_MULTISTAGE = "no_multistage"
    UNNECESSARY_FILES = "unnecessary_files"
    NO_DOCKERIGNORE = "no_dockerignore"
    RUN_NOT_MERGED = "run_not_merged"
    NO_BUILDKIT_CACHE = "no_buildkit_cache"
    LATEST_TAG = "latest_tag"
    ROOT_USER = "root_user"
    APT_NO_VERSION_PIN = "apt_no_version_pin"

@dataclass
class Issue:
    issue_type: IssueType
    severity: Severity          # INFO / WARNING / CRITICAL
    title: str
    description: str
    line_number: Optional[int]  # 精确到行号
    suggestion: str = ""

@dataclass
class OptimizationSuggestion:
    title: str
    description: str
    priority: int               # 1=最高
    estimated_savings: str = ""
    example_before: str = ""
    example_after: str = ""

@dataclass
class AnalysisResult:
    dockerfile_path: str
    base_image: str
    total_layers: int
    issues: list[Issue]
    suggestions: list[OptimizationSuggestion]
    layers: list[LayerInfo]
    estimated_size_mb: Optional[float]
    has_multistage: bool
    has_dockerignore: bool
```

**设计要点：**
- `Issue` 包含 `line_number` 字段，可精确定位问题所在行
- `OptimizationSuggestion` 包含 `example_before` / `example_after`，支持前后对比展示
- `AnalysisResult` 作为全链路数据载体，在分析→优化→报告三个阶段透传
- 使用 `str` 继承 `Enum` 实现 JSON 序列化兼容

### 3.2 Dockerfile 分析引擎 — `image_analyzer.py`

**主入口接口：**

```python
def analyze_dockerfile(path: str) -> AnalysisResult
```

**核心流程：**

1. **指令解析** `parse_dockerfile()` — 正则匹配 `^([A-Z]+)\s+(.*)` + `\` 续行合并
2. **基础镜像提取** `extract_base_image()` — 从第一个 FROM 指令提取
3. **多阶段检测** `detect_multistage()` — 统计 FROM 指令数量 > 1
4. **层构建** `build_layers()` — 为每条指令构建 LayerInfo（含缓存标记）
5. **问题检测** `detect_issues()` — 基于规则的 8 项检测

### 3.3 优化建议 & 重写引擎 — `optimizer.py`

**接口：**

```python
def generate_suggestions(result: AnalysisResult) -> list[OptimizationSuggestion]
def rewrite_dockerfile(result: AnalysisResult) -> str
```

**建议生成策略：** 基于分析结果按优先级动态生成 7 类建议，每条包含：
- 优化前后代码对比示例
- 预估节省量（如 "60-80% 基础镜像体积"）
- 优先级排序（1=最高）

**建议类型：**

| # | 建议 | 预估节省 |
|---|------|---------|
| 1 | 使用精简基础镜像 | 60-80% 基础镜像体积 |
| 2 | 使用多阶段构建 | 40-70% 总镜像体积 |
| 3 | 合并 RUN 指令 | 每合并一层约 1-5MB |
| 4 | 清理包管理器缓存 | 10-50MB |
| 5 | 添加 .dockerignore | 减少构建上下文传输时间 |
| 6 | pip 禁用缓存 | 10-30MB |
| 7 | 使用 BuildKit 缓存挂载 | 加速构建，减少网络传输 |

**关键代码 — Dockerfile 重写（RUN 合并逻辑）：**

```python
def rewrite_dockerfile(result: AnalysisResult) -> str:
    optimized = []
    run_buffer = []
    for line in lines:
        stripped = line.strip()
        # 替换基础镜像
        if stripped.upper().startswith("FROM "):
            if alt and not result.has_multistage:
                optimized.append(f"FROM {alt}")
            else:
                optimized.append(line)
            continue
        # 收集连续 RUN 指令
        if stripped.upper().startswith("RUN "):
            run_buffer.append(stripped[4:].strip())
            continue
        # 遇到非 RUN 指令时，合并输出
        if run_buffer:
            _flush_run_buffer(optimized, run_buffer)
            run_buffer = []
        optimized.append(line)

def _flush_run_buffer(output, commands):
    if len(commands) == 1:
        output.append(f"RUN {commands[0]}")
    elif len(commands) > 1:
        merged = " && \\\n    ".join(commands)
        output.append(f"RUN {merged}")
```

## 第五章 技术亮点

### 5.1 纯规则引擎，零外部依赖分析

不依赖 Docker daemon 或镜像 registry，纯静态解析 Dockerfile 即可完成分析。通过维护 `IMAGE_SIZE_ESTIMATES` 映射表（覆盖 30+ 常见镜像）实现镜像大小估算，无需实际拉取镜像。

### 5.2 精确到行号的问题定位

每个 `Issue` 对象携带 `line_number`，结合续行合并的解析逻辑，即使 Dockerfile 使用 `\` 续行也能准确定位问题行。

### 5.3 自动 Dockerfile 重写

不仅指出问题，还自动重写 Dockerfile：
- 替换精简基础镜像
- 合并连续 RUN 指令（使用 `&&` + `\` 续行格式）
- 添加 .dockerignore 提示

### 5.4 多格式报告输出

同一分析结果可输出为终端（Rich）、Markdown、HTML 三种格式，满足不同场景需求。

### 5.5 可配置的规则引擎

通过 `config.yaml` 可开关每条检测规则，设置层数阈值、大小阈值等参数，支持自定义精简镜像映射。

### 5.6 多入口架构

同一套分析引擎被四个入口复用：
- **CLI**：命令行直接分析
- **REST API**：供外部系统集成调用
- **Web Dashboard**：浏览器可视化分析
- **macOS GUI**：桌面客户端一键操作

## 第六章 面试常见问题

**Q1: 你是怎么做 Dockerfile 解析的？**

> 用正则表达式 `^([A-Z]+)\s+(.*)` 匹配每行的指令和参数。处理了 `\` 续行的情况——先做续行合并再解析。不依赖任何 Docker SDK，纯文本解析。

**Q2: 怎么估算镜像大小的？**

> 维护了一个 `IMAGE_SIZE_ESTIMATES` 字典，包含 30+ 常见镜像的大小（单位 MB）。数据来源是 Docker Hub 上的官方镜像大小。这是估算值，但对于优化建议来说精度足够。

**Q3: 检测规则是怎么设计的？**

> 纯规则引擎，每个规则是一个独立的检测函数。比如检测大基础镜像就是查映射表；检测缓存未清理就是检查 RUN 指令中是否包含清理命令。规则可通过 config.yaml 开关。

**Q4: Dockerfile 重写的逻辑是什么？**

> 逐行扫描，遇到 FROM 就替换为精简镜像；遇到连续 RUN 就缓存起来，遇到非 RUN 指令时用 `&&` 合并输出。本质上是一个单遍扫描 + 缓冲区刷新的状态机。

**Q5: 项目的技术挑战在哪？**

> 1) Dockerfile 语法的续行处理，需要正确合并多行；2) 规则的准确性和误报控制——比如只有存在编译工具时才建议多阶段构建；3) 重写后 Dockerfile 的语义保持，合并 RUN 时不能改变执行顺序。

**Q6: 如何扩展新的检测规则？**

> 在 `IssueType` 枚举中新增类型，在 `detect_issues()` 函数中添加检测逻辑，在 `SLIM_ALTERNATIVES` / `IMAGE_SIZE_ESTIMATES` 中补充数据。整个设计是开闭原则——新增规则不需要修改已有代码。

**Q7: 为什么选择 FastAPI 而不是 Flask？**

> FastAPI 原生支持 Pydantic 数据校验和自动生成 OpenAPI 文档。`AnalysisResponse` 的字段类型校验是声明式的，不需要手写验证逻辑。而且 async 支持对文件上传场景更友好。

**Q8: 多入口架构是怎么设计的？**

> 核心分析引擎（image_analyzer + optimizer + reporter）是独立的 Python 模块，不依赖任何 Web 框架。CLI、API、Web Dashboard、GUI 四个入口都是薄封装，调用相同的分析接口。这样既避免了代码重复，也便于独立部署。
